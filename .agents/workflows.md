# Порядок работы

## 1. Перед изменениями

```bash
git status
```

В репозитории может параллельно работать другой агент или человек. Если в дереве есть
чужие незакоммиченные изменения — **не трогайте их**: не делайте `git checkout .`,
`git reset --hard`, `git stash` и не коммитьте чужие файлы под своим сообщением. Если вы
видите `<<<<<<<` в файлах, которых не касались, — остановитесь и сообщите пользователю.

Затем прочитайте:

- [`conventions.md`](conventions.md) — обязательные границы;
- `CLAUDE.md` — карта репозитория, команды, владение состоянием;
- `packages/protocol/README.md` — если задача касается RPC.

Установка: `pnpm install` (Node 22+, pnpm 10.34, версии закреплены в `package.json`).

## 2. Реализация

Направление зависимостей:

```
apps/web/app            (маршруты Next.js, RPC-маршрут)
        v
apps/web/components     (оболочка, секции, примитивы, store)
        v
apps/web/lib            (rpc: сервисы + клиент + codec; screenkit: данные, i18n; db)
        v
packages/protocol       (контракты .proto и сгенерированные привязки)
packages/screenkit-core (типы и манифесты вставок)
packages/inserts/*      (сцены вставок; зависят только от screenkit-core)
```

Порядок для новой операции: `.proto` → `pnpm --filter @mixture/protocol generate` →
реализация `*.service.ts` → регистрация в `router.ts` → метод в `store.tsx` или клиент в
секции → интерфейс → словарь i18n (RU и EN) → тест.

Новая вставка: пакет в `packages/inserts/<slug>` с `manifest` и `Scene` (см.
`packages/inserts/README.md`), при необходимости карточка в `screenkit.insert.json`;
`sync-inserts` подхватит её автоматически перед `dev`/`build`.

## 3. Проверка

Минимум для любой задачи:

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm check:protocol-generation   # если менялись .proto
pnpm build                       # без DATABASE_URL
```

Полный локальный шлюз: `pnpm check`.

Запуск одного файла тестов:

```bash
pnpm --filter web test -- lib/rpc/cloud/config.test.ts
```

Ручная проверка интерфейса: `pnpm dev`, затем разделы `?view=library`, `?view=preview`,
`?view=cloud`; тема светлая и тёмная; ширина 390px и 1280px.

## 4. Отчёт

Приводите **реальный вывод** с числами, а не утверждение «всё проходит». Явно
перечисляйте, что осталось непокрытым и что не запускалось («написано, не запускалось»
— нормальный статус).

Если отрицательный тест должен доказывать защиту от регрессии — убедитесь, что он падает
при откате исправления, и укажите это в отчёте.

## 5. Коммит

Conventional Commits:

```
<тип>(<область>): <краткое описание в повелительном наклонении>
```

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`,
`revert`. Области: `web`, `protocol`, `cloud`, `inserts`, `docs`, `ci`.

Правила:

- не коммитьте в `master` напрямую — работайте в ветке и открывайте pull request;
- индексируйте только свои файлы, перечисляя пути явно; `git add -A` захватит чужую
  незакоммиченную работу;
- перед коммитом просмотрите `git diff --cached --stat` и убедитесь, что в индексе нет
  секретов, `.env`, токенов и ключей;
- трейлеры атрибуции (`Co-Authored-By`, ссылка на сессию агента) допустимы — они не
  снимают ответственность с человека, отправившего изменение (см. `AI_USAGE_POLICY.md`).

## 6. Обновление документации

- `CLAUDE.md` и `.agents/` — если менялись команды, границы или владение состоянием;
- `packages/protocol/README.md` — если менялся контракт;
- `README.md` — если менялись возможности, видимые пользователю.
