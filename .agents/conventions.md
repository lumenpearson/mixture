# Границы и соглашения

Каждый пункт ниже — не стилистическое предпочтение, а инвариант. Рядом указано, чем он
проверяется.

## Проверяются скриптами и сборкой

### Свежесть сгенерированных Protobuf-привязок

После правки любого `.proto` обязательно:

```bash
pnpm --filter @mixture/protocol generate
pnpm check:protocol-generation
```

Скрипт `scripts/check-protocol-generation.mjs` перегенерирует `packages/protocol/src/gen`
и сравнивает SHA-256 до и после. Незакоммиченный результат генерации роняет проверку.

### Типы, линт, тесты

```bash
pnpm typecheck   # tsc --noEmit во всех пакетах
pnpm lint        # eslint (eslint-config-next) + buf lint
pnpm test        # vitest, офлайн и детерминированно
pnpm build       # next build без DATABASE_URL обязан проходить
```

`next.config.mjs` не должен скрывать ошибки типов: сборка с `ignoreBuildErrors: true` не
считается зелёной.

## Проверяются ревью и тестами

### Транспорт

Все прикладные операции идут через ConnectRPC поверх **бинарного gRPC-Web** из одного
маршрута `apps/web/app/api/rpc/[...path]`. Контракты — `packages/protocol/proto/mixture/*/v1`.
Никаких новых REST-эндпоинтов, server actions и произвольного JSON для бизнес-операций:
новая операция — это новый `rpc` в существующем сервисе или новый сервис в `.proto`, его
реализация в `apps/web/lib/rpc/*.service.ts` и регистрация в `apps/web/lib/rpc/router.ts`.

Нативный gRPC (HTTP/2 с трейлерами) не включается: приложение живёт на serverless-функциях
Vercel поверх HTTP/1.1.

Исключения — только статика: тексты лицензий из `public/licenses/*`, экспортированные
Next-вставки из `public/screenkit-inserts/*`, манифест и иконки.

### Данные

- Изменение значения существующего поля `.proto` — ломающее изменение: добавляйте новое
  поле, старое помечайте `[deprecated = true]`, номера не переиспользуйте.
- Схема Postgres (`apps/web/lib/db/schema.ts`) меняется только с одновременной правкой
  чтения в `library.server.ts` и записи в `library.service.ts`; текстовые колонки
  `device`, `aspect`, `status` хранят доменные строки (`"needs review"`), а не номера enum.
- Мутации библиотеки проверяют вход через zod до обращения к базе; цвет категории
  проходит только как `var(--accent-*)`, hex или `rgba(...)`.
- Без `DATABASE_URL` приложение обязано работать в режиме «только чтение» на встроенных
  данных — и при сборке, и в рантайме.

### Облако

- Файлы облака хранятся в корне репозитория облака; `cloud.config.json` там же —
  единственный источник правил видимости и доступа. Сервер не хранит свои копии прав.
- Роли монотонны: `anonymous < viewer < editor < owner`. Скрытые файлы видит только
  владелец; приватные — от viewer; публичные — все, если `allowAnonymousPublic`.
- Токены и ключи доступа никогда не сохраняются на сервере. Ключ хранится в конфиге
  только как sha256; исходный ключ показывается один раз при создании.
- Путь валидируется до любого обращения к GitHub: без `..`, `.git`, управляющих символов;
  `cloud.config.json` нельзя записать или удалить как обычный файл.
- Невидимый файл отвечает так же, как отсутствующий (`not_found`), чтобы не раскрывать
  структуру хранилища.

### Раскладка и оформление

- Оболочка — рельса, панель категорий, контент — не скроллится целиком: `100dvh`,
  скроллятся только области внутри `ScrollArea`.
- Цвета берутся из токенов `globals.css` (`--panel-*`, `--control-*`, `--accent-*`,
  `--text-*`), а не из литералов. Новые палитры добавляются как `[data-palette="…"]`.
- Все анимации уважают `data-motion` и флаги `data-motion-*`: новая анимация получает
  класс, отключаемый через `html[data-motion-sections="off"]` или аналог.
- Тексты интерфейса — через словарь `lib/screenkit/i18n.ts` в обеих локалях; строки в
  компонентах не хардкодятся. Проверка: число ключей RU и EN совпадает.

## Код

- Интерфейс и README — на русском; код, идентификаторы и комментарии — на английском.
- TypeScript строгий (`tsconfig.base.json`, `strict: true`).
- Пишите код в стиле окружающего: та же плотность комментариев, те же имена и идиомы.
- Комментарий объясняет **почему**, а не пересказывает код.
- `apps/web/lib/screenkit/generated-inserts.ts` и `licenses.generated.json` генерируются
  скриптами перед `dev` и `build` — не правьте вручную.

## Владение состоянием

- `ScreenkitProvider` (`components/screenkit/store.tsx`) владеет клиентским состоянием:
  раздел, выбранная вставка, фильтры, настройки превью, библиотека (из RPC), избранное,
  токен редактирования. Компоненты вызывают его методы и не ходят в RPC напрямую, кроме
  секции облака и changelog, у которых свои клиенты.
- Тема, палитра, масштаб, glow — `components/screenkit/theme.tsx`; движение —
  `motion.tsx`. Они пишут атрибуты на `<html>` и `localStorage`.
- `localStorage` владеет всем, что сохраняет браузер; ключи с префиксом `screenkit-`
  (locale, palette, palette-recent, gradients, scale, glass, motion, motion-features,
  content-width, category-panel-width, layout, favorites, library-list, kind-overrides,
  wizard-draft, player, rpc, desktop, cloud-settings, cloud-favorites) и `mixture-`
  (edit-token, cloud-token, cloud-key). `sessionStorage` — только кэши
  (`screenkit-library-cache-v2`, `screenkit-changelog-cache-v3`). Полный список с
  назначением — в `CLAUDE.md`; он проверяется тестом
  `lib/screenkit/storage-keys.test.ts`, так что новый ключ добавляется в список тем же
  изменением.
- Встроенные вставки (`lib/screenkit/data.ts`) и пакеты вставок (`packages/inserts/*`) —
  неизменяемая конфигурация, а не состояние.

## Тесты

- `pnpm test` остаётся офлайн и детерминированным: сеть, база и GitHub не участвуют.
- Тесты лежат рядом с предметом (`foo.ts` → `foo.test.ts`), запускаются vitest из
  `apps/web`.
- Тест на роль, видимость или валидацию пути обязан иметь отрицательный случай, который
  падает при откате исправления.
