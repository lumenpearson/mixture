# Релизы

Каждый коммит в `master`, прошедший все проверки `ci`, автоматически становится
GitHub Release: исходный код этого коммита, установщики и исполняемые файлы для
Windows, необязательный APK для Android и контрольные суммы для всего перечисленного.
Ничего не нужно запускать руками — тег и релиз создаёт
[`.github/workflows/release.yml`](../../.github/workflows/release.yml).

## Как это запускается

```
push в master ──> ci ──(conclusion == success)──> release
```

`release` подписан на `workflow_run` рабочего процесса `ci` с типом `completed`. Одной
подписки мало: `workflow_run` срабатывает на любом завершённом прогоне `ci`, в том числе
на прогоне из pull request, а `head_branch` у форка — имя ветки **внутри форка**, и у
свежего форка это тоже `master`. Поэтому задача `guard` требует ещё двух условий:

```yaml
github.event.workflow_run.event == 'push'
github.event.workflow_run.head_repository.full_name == github.repository
```

Без них хватило бы обычного pull request из форка, чтобы чужое дерево собралось на
Windows-раннере с секретами подписи и вышло официальным релизом. Прошедший эти условия
прогон даёт ровно тот `head_sha`, на котором проверки были зелёными, — не «текущую
голову `master`», которая могла уйти вперёд.

Группа параллелизма — `release-<sha релизуемого коммита>`, `cancel-in-progress: false`.
Группа держит не больше одного *ожидающего* прогона, поэтому общая группа на ветку
теряла бы релизы: три коммита подряд — и второй, стоящий в очереди, молча вытесняется
третьим. Тег уникален для коммита, за один тег релизы не спорят, так что разные коммиты
идут параллельно, а начатый релиз не отменяется никогда. Права рабочего процесса — только
`contents: write` (создать тег и релиз), у сборочных задач и того меньше: `contents: read`.

`ci` запускается и на `pull_request`, и на `push` в `master`. Группа параллелизма там по
той же причине разная: pull request — по ветке, с `cancel-in-progress`, push — по sha
коммита, чтобы прогон, которого ждёт релиз, не был ни отменён, ни вытеснен из очереди
следующим коммитом.

Ручной запуск — `workflow_dispatch` с флажком `force`:

- флажок стоит (по умолчанию) — релиз собирается с текущей головы `master`;
- флажок снят — сухой прогон: тег вычисляется и проверяется на занятость, ничего не
  собирается и не публикуется.

Оба пути упираются в одно ограничение: **существующий тег не переиспользуется**. Если тег
уже есть, задача `guard` останавливает весь процесс с явным сообщением.

## Тег и заголовок

Тег календарный и уникален для коммита:

```
v<ГГГГ.ММ.ДД>-<7 символов sha>      например  v2026.09.03-c7ddcf0
```

Дата — дата коммита в UTC, а не время запуска раннера и не его часовой пояс. Заголовок
релиза — `mixture · screenkit <тег>`. Считает это
[`scripts/release/version.mjs`](../../scripts/release/version.mjs):

```bash
node scripts/release/version.mjs --sha "$(git rev-parse HEAD)"
node scripts/release/version.mjs --sha "$(git rev-parse HEAD)" --format tag
```

Тег создаёт `softprops/action-gh-release` через API GitHub, из `target_commitish`
released-коммита. Бот не пушит теги в репозиторий.

### Версия внутри артефактов

Тег — идентичность релиза на GitHub, но внутри Windows видит трёхчастный номер версии, и
календарный тег на него не ложится: MSI сравнивает три поля, major и minor — не больше
255, patch — не больше 65535. Поэтому `version` в `tauri.conf.json` (`0.1.0`, для
локальных сборок) рабочий процесс переопределяет накладкой:

```
0.1.<номер прогона release>      github.run_number, одно значение на релиз
```

Этот номер попадает в `ProductVersion` NSIS-установщика и в ключ удаления, в
`ProductVersion` MSI и в ресурс версии `.exe` (его пишет `tauri-build` из `version`
конфигурации), а `notes.mjs` печатает его в описании релиза. Без этого каждая сборка
представлялась бы как `0.1.0`, и по установленному приложению нельзя было бы сказать, из
какого релиза оно взято.

Описание релиза рендерит
[`scripts/release/notes.mjs`](../../scripts/release/notes.mjs): список коммитов с
прошлого релизного тега (с номерами pull request, если они есть в заголовке; длиннее 200
строк список не бывает, вместо остального идёт пометка, что он обрезан), таблица файлов,
версия сборки, блок совместимости, предупреждение о неподписанных сборках и команда
проверки сумм. Сверху GitHub добавляет свои автоматические заметки (`generate_release_notes`).

### Исходные архивы

Собираются на ubuntu из `git archive` ровно того коммита: без `.git` и без
`node_modules`, но **с `pnpm-lock.yaml`** — он лежит в репозитории. Поэтому из
распакованного архива работает

```bash
pnpm install --frozen-lockfile
```

и даёт те же версии зависимостей, с которыми собирался релиз. Четыре формата — `.zip`,
`.tar.gz`, `.tar.xz`, `.7z` — упаковывает
[`scripts/release/archive.mjs`](../../scripts/release/archive.mjs); `7z` на ubuntu
приезжает пакетом `p7zip-full`, на windows-раннере он уже есть.

## Совместимость с Windows

Минимум — **Windows 10 версии 1803 (сборка 17134)**. Порог задаёт не приложение, а среда
выполнения Microsoft Edge WebView2: на более старых сборках Evergreen-версия не
устанавливается. Поддержка WebView2 для Windows 7, 8 и 8.1 прекращена, поэтому эти
системы не поддерживаются.

| Система                    | x64 | ARM64 | x86 (32 бита) |
| -------------------------- | --- | ----- | ------------- |
| Windows 10 1803 и новее    | да  | да    | да            |
| Windows 11                 | да  | да    | да (WoW64)    |
| Windows Server 2016 и новее | да  | —     | да            |

- на 64-разрядной системе ставьте x64-сборку; x86 остаётся для 32-разрядных установок;
- в Windows 11 WebView2 уже установлен, установщик его не трогает;
- портативная сборка среду выполнения не несёт — если окно пустое, поставьте
  [Evergreen Bootstrapper](https://go.microsoft.com/fwlink/p/?LinkId=2124703).

Настройки «минимальная версия Windows» бандлеры Tauri не дают — версию ОС ни NSIS-, ни
WiX-шаблон не проверяют. Что они дают — порог версии WebView2,
`bundle.windows.minimumWebview2Version`. В
[`tauri.conf.json`](../../apps/desktop/src-tauri/tauri.conf.json) его нет: рабочий
процесс дописывает `"minimumWebview2Version": "110.0.0.0"` **только в накладку
онлайн-прохода** (`embedBootstrapper`). 110 — первая версия WebView2 без поддержки
Windows 7, 8 и 8.1, то есть первая, которая существует только для поддерживаемых систем.

Порог не «просит обновиться», а прерывает установку. Вложенную среду выполнения
NSIS-шаблон использует только там, где WebView2 нет вовсе; если он есть, но старее
порога, шаблон идёт другой веткой: читает путь EdgeUpdate из реестра и запускает
обновление по сети, а при ненулевом коде возврата показывает `MB_ABORTRETRYIGNORE` и
завершает работу, если пользователь не выбрал «Пропустить». Ключа `/SD` там нет, поэтому
тихая установка (`/S`) мимо этого диалога не проходит.

Отсюда и правило: у offline-установщика порога нет. Он существует ровно для машины без
сети, где эта ветка гарантированно провалилась бы, — и с порогом отказался бы ставиться
именно там, где нужен. MSI собирается в онлайн-проходе и порог получает
(`minimum_webview2_version`), но сравнение версий там строковое, средствами MSI, поэтому
срабатывает оно не всегда. Практического вреда нет: Evergreen-канал давно ушёл далеко за
110.

### Чего нет для ARM64

Offline-установщика для ARM64 нет. Offline-режим встраивает Evergreen Standalone
Installer, а `download_webview2_offline_installer`
(`crates/tauri-bundler/src/bundle/windows/util.rs`) знает только две ссылки — x64 и x86 —
и для всего остального берёт x86. ARM64-машина получила бы x86-среду выполнения, которую
ARM64-приложение загрузить не может, поэтому эта сборка пропускается.

MSI для ARM64, наоборот, собирается: Tauri тянет WiX 3.14.1, а `tauri-bundler`
сопоставляет `Arch::AArch64` с `-arch arm64`. Проверено по исходникам
`tauri-cli` 2.11.4 — версии, закреплённой в `apps/desktop/package.json`, — но не запуском
на Windows-раннере.

Задачи в матрице помечены полями `msi` и `offline`, а шаг «what this target produces»
печатает в лог, что именно собирается и почему пропущено остальное.

## Установщики

NSIS-установщик:

- `installMode: "both"` — пользователь выбирает установку для себя или на всю машину;
- языки русский и английский, с диалогом выбора языка (`displayLanguageSelector`);
- ярлыки на рабочем столе и в меню «Пуск», папка `mixture · screenkit`;
- деинсталлятор в «Приложения и возможности»;
- `allowDowngrades: true` — поверх свежей сборки можно поставить старую.

MSI собирается WiX для всех трёх архитектур. Язык у него один — русский: WiX делает
отдельный файл на каждый язык, а имена файлов в релизе фиксированные. Меняется это в
`bundle.windows.wix.language` в
[`tauri.conf.json`](../../apps/desktop/src-tauri/tauri.conf.json).

Установщик и переносимая сборка собираются из одного `tauri.conf.json`; отличия релиза
от локальной сборки лежат в накладке, которую рабочий процесс пишет в `$RUNNER_TEMP` и
передаёт через `tauri build --config`. Накладок две, по одной на проход
(`embedBootstrapper` и `offlineInstaller`), и в них: режим установки WebView2, порог
версии WebView2 (только в онлайн-проходе), версия сборки, набор возможностей и — если
заведены секреты — отпечаток сертификата подписи. Второй конфигурации в репозитории нет.

### Права окна в опубликованной сборке

Накладка задаёт `app.security.capabilities: ["default"]`. В
`apps/desktop/src-tauri/capabilities/` файлов два:

| Файл           | Где действует                                             |
| -------------- | --------------------------------------------------------- |
| `default.json` | локальная страница из бандла (`tauri://localhost`); в релизе только он |
| `dev.json`     | `http://localhost:3000` — адрес, который открывает `tauri dev`         |

Сборка, которая набор не называет (`pnpm dev`, `cargo check`, локальный `tauri build`),
включает оба файла; релиз называет `default`, и `dev.json` в опубликованный бинарник не
попадает. Разница существенная: `http://localhost:3000` — это что угодно, что слушает
этот порт на машине пользователя, а права там не декоративные: управление окном,
`shell:allow-open`, `dialog:allow-open`, файловая система в каталоге данных и команды
`local_*`, читающие выданную папку.

Второй проход стоит времени: `--config` меняет `TAURI_CONFIG`, скрипт сборки
`tauri-build` перезапускается и крейт перелинковывается. Зависимости при этом уже
собраны и лежат в кэше `Swatinem/rust-cache`, поэтому пересобирается только приложение.

### Что лежит внутри артефактов

Интерфейс больше не грузится с сайта — он лежит в самом установщике. Windows-задача
поэтому ставит **два** рабочих пространства
(`pnpm install --frozen-lockfile --filter web... --filter @mixture/desktop...`) и перед
сборкой выполняет экспорт: `pnpm --filter web build:desktop` кладёт статический Next-экспорт
в `apps/web/out/desktop`, а `frontendDist` в `tauri.conf.json` указывает туда. Шаг задан
явно, а `beforeBuildCommand` в накладке очищен: бандлер запускается по два раза на
архитектуру, и хук экспортировал бы сайт заново на каждый проход.

Адрес api вшивается в экспорт на этом же шаге: `NEXT_PUBLIC_MIXTURE_API_URL`
(`https://mixture-codeilluminators.vercel.app`) в окружении Windows-задачи. Это адрес
**api**, а не сайта: окно открывает файл с диска, наружу уходят только вызовы rpc.
Указать другой стенд можно и без пересборки — в настройках приложения, раздел «rpc».

Итого в каждом установщике и в переносимом архиве: исполняемый файл оболочки,
статический интерфейс (`.html`, `.js`, `.css`, шрифты, иконки, тексты лицензий) и
встроенный каталог вставок на момент сборки. Ни `node_modules`, ни базы данных, ни
токенов внутри нет; `apps/mobile` на Windows-раннер по-прежнему не приезжает.

## Подпись

Сборки **не подписаны**. При первом запуске Windows SmartScreen показывает «Windows
защитила ваш компьютер»; открыть — «Подробнее» → «Выполнить в любом случае». Пока
подписи нет, доверие даёт `SHA256SUMS.txt`.

Чтобы включить подпись, не трогая рабочий процесс:

1. получите сертификат для подписи кода в виде `.pfx`;
2. переведите его в base64:

   ```bash
   base64 -w0 certificate.pfx
   ```

   ```powershell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("certificate.pfx"))
   ```

3. в настройках репозитория — Settings → Secrets and variables → Actions → New
   repository secret — заведите два секрета:

   | Секрет                         | Значение                     |
   | ------------------------------ | ---------------------------- |
   | `WINDOWS_CERTIFICATE`          | base64 из шага 2             |
   | `WINDOWS_CERTIFICATE_PASSWORD` | пароль от `.pfx`             |

4. следующий релиз подпишет сборки сам.

Секрет в окружении задачи не лежит: там его прочитал бы build-скрипт любой зависимости
при `cargo build` и любой lifecycle-скрипт при `pnpm install`. Условие `if:` у шага
контекст `secrets` не видит, поэтому шагов два: `is a signing certificate configured`
получает `WINDOWS_CERTIFICATE` и только проверяет, что он не пуст, а
`import the code signing certificate` выполняется по его выводу — импортирует `.pfx` в
хранилище пользователя, удаляет временный файл и отдаёт отпечаток сертификата в накладку
конфигурации (`certificateThumbprint`, `digestAlgorithm: sha256`, метка времени
DigiCert). Больше секрет не передаётся ни одному шагу. Без секретов оба шага ничего не
делают, и релиз собирается неподписанным.

Сам `.pfx` и пароль в репозиторий не попадают ни в каком виде. Сертификат на аппаратном
токене (EV) так использовать нельзя — для него нужен `bundle.windows.signCommand` и
внешняя служба подписи.

## Контрольные суммы

`SHA256SUMS.txt` собирает
[`scripts/release/checksums.mjs`](../../scripts/release/checksums.mjs) в формате
`sha256sum`: 64 шестнадцатеричных символа, два пробела, имя файла.

```powershell
Get-FileHash .\mixture-screenkit-<тег>-windows-x64-setup.exe -Algorithm SHA256
```

```bash
sha256sum --check SHA256SUMS.txt
```

## Android

Задача `android` выполняется только если в released-коммите есть
`apps/mobile/package.json` (проверка `hashFiles` в задаче `guard`). Если каталога нет,
задача пропускается и релиз выходит без APK — это не ошибка.

Шаги повторяют задачу `apk` из [`.github/workflows/mobile.yml`](../../.github/workflows/mobile.yml):
`NPM_CONFIG_NODE_LINKER=hoisted` (gradle и автолинковка React Native читают плоский
`node_modules`, поэтому здесь и только здесь установка идёт без `--frozen-lockfile`),
`expo prebuild --platform android --no-install`, затем `gradlew assembleRelease` с
явно подставленным хранилищем ключей.

Подпись: если заведены секреты `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS` и `ANDROID_KEY_PASSWORD`, берётся настоящее хранилище. Без них
задача создаёт одноразовое отладочное — APK ставится из файла, но не годится ни для
Google Play, ни для обновления уже установленного приложения.

Второго APK при этом не появляется. Тег создаётся через API с `GITHUB_TOKEN`, а события
от `GITHUB_TOKEN` не порождают прогонов рабочих процессов (кроме `workflow_dispatch` и
`repository_dispatch`), поэтому подписка `mobile.yml` на `push: tags: ["v*"]` от
релизного тега не срабатывает — она достижима только для тега, отправленного руками.
Что с ней делать, решается отдельно: `mobile.yml` в объём этой работы не входил.

## Провал сборки

- любая упавшая Windows-цель роняет релиз целиком — половинчатых релизов не бывает;
- упавшие исходные архивы роняют релиз;
- задача `android` необязательна в обе стороны: и пропущенная, и упавшая оставляют релиз
  без APK, но не отменяют его. Шаг «list what will be published» пишет предупреждение с
  исходом задачи, чтобы отсутствие файла было видно в логе;
- все файлы прикрепляются одним шагом `softprops/action-gh-release@v2` с
  `fail_on_unmatched_files: true`. Маска `assets/*` всегда что-то находит — исходные
  архивы есть в любом релизе, — поэтому необязательный APK её не роняет.

Кэши: `Swatinem/rust-cache@v2` для cargo (ключ — триплет цели) и кэш pnpm в
`actions/setup-node`. Три Windows-цели идут параллельно; ориентир по времени — меньше
40 минут на весь процесс, потолок задачи — 45 минут.

## Локальная проверка скриптов

```bash
pnpm test:release      # то же самое, что node scripts/release/selftest.mjs
```

Проверяет то, что нельзя починить после публикации: тег не съезжает от часового пояса
раннера, у каждого имени файла есть строка «кому» и ни одна строка «кому» не описывает
файл, которого в релизе нет, длинный список коммитов обрезается и говорит об этом, номер
версии сборки попадает в описание, формат `SHA256SUMS.txt` читается `sha256sum --check`,
архивы собираются.

Скрипты релиза лежат вне пакетов workspace, поэтому `pnpm test` (turbo) до них не
достаёт. Отдельный шаг `pnpm test:release` есть в `ci` и в `pnpm check` — иначе эти
проверки были бы советом, а не воротами.

Сам `tauri.conf.json` проверяется компиляцией: `generate_context!` разбирает его в
скрипте сборки и отклоняет незнакомое поле, поэтому после правки настроек бандлера
достаточно

```bash
cargo check --locked --manifest-path apps/desktop/src-tauri/Cargo.toml
```

Синтаксис и выражения рабочих процессов — `actionlint` (в CI его нет, это локальный
инструмент).

Собрать установщик локально (нужна Windows, Rust с MSVC и Node 22+):

```powershell
pnpm install                                  # весь workspace: экспорт собирает apps/web
pnpm --filter @mixture/desktop build:x64     # nsis + msi, x86_64-pc-windows-msvc
pnpm --filter @mixture/desktop build:arm64   # nsis + msi, aarch64-pc-windows-msvc
pnpm --filter @mixture/desktop build:x86     # nsis + msi, i686-pc-windows-msvc
```

Экспорт интерфейса запускать руками не нужно: `beforeBuildCommand` в `tauri.conf.json`
вызывает `pnpm --filter web build:desktop` сам. Без `NEXT_PUBLIC_MIXTURE_API_URL` бандл
соберётся, но api в нём задан не будет — экспорт об этом предупреждает, а указать адрес
можно потом в настройках приложения.

Google Play, подписанных сборок «из коробки» и релизов с веток, кроме `master`.
