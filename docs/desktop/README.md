# Десктоп · Windows-версия на Tauri 2

`apps/desktop` — это настоящее локальное приложение, а не окно вокруг сайта. Интерфейс
тот же самый Next.js-проект, но он лежит **внутри** установленного приложения:
статический экспорт `apps/web` попадает в бандл и открывается с диска. Наружу уходят
только прикладные операции — библиотека, список изменений, облако, — и они идут по rpc в
развёрнутый api. Плюс то, чего браузер не умеет надёжно, — доступ к локальной папке на
диске. Сборка выходит установщиком NSIS (`.exe`), установщиком WiX (`.msi`) и переносимым
`.exe` в архиве.

- продукт: `mixture · screenkit`, идентификатор `ru.mixture.screenkit`
- окно: 1280×800, минимум 720×560, **без системной рамки** — заголовок рисует сама
  страница
- интерфейс: `apps/web/out/desktop` (`frontendDist`), собирается
  `pnpm --filter web build:desktop`
- api: `NEXT_PUBLIC_MIXTURE_API_URL` на момент экспорта, иначе — тот же origin, что и у
  страницы; в отладочной сборке `tauri dev` открывает `http://localhost:3000`

## Окно без рамки

`decorations(false)` в `src-tauri/src/lib.rs`. Системного заголовка нет — вместо него
верхняя панель на стороне сайта (`components/screenkit/desktop/titlebar.tsx`) с
названием, разделом, часами и кнопками «свернуть», «развернуть», «закрыть». Панель и её
пассивные дети помечены `data-tauri-drag-region`, поэтому окно тянется за любое место
панели, кроме кнопок.

Рамки для изменения размера при этом остаются: окно без декораций, но с
`resizable(true)`, сохраняет в Windows и границы для растягивания, и прилипание к краям,
и Aero Shake — tao держит `WS_THICKFRAME` и переопределяет расчёт неклиентской области.
Отдельного обходного пути не нужно; важно не терять `resizable(true)`.

Права на управление окном перечислены поимённо в `capabilities/default.json` — ровно то,
что вызывает страница:

| Право                       | Кто вызывает                                          |
| --------------------------- | ----------------------------------------------------- |
| `allow-start-dragging`      | `data-tauri-drag-region` в `titlebar.tsx`             |
| `allow-minimize`            | кнопка «свернуть»                                      |
| `allow-toggle-maximize`     | кнопка «развернуть» и двойной щелчок по панели        |
| `allow-close`               | кнопка «закрыть»                                       |
| `allow-maximize`            | настройка «открывать развёрнутым»                     |
| `allow-set-always-on-top`   | настройка «поверх других окон»                         |
| `allow-set-min-size`        | настройка «минимальный размер»                         |
| `window-state:allow-restore-state` | настройка «запоминать размер и положение»       |

`set-size` и `set-position` не выданы: геометрию страница не задаёт — ею владеет плагин
состояния окна (ниже). Всё, что только читает состояние окна (`is-maximized`,
`outer-size`, `internal-toggle-maximize`), уже входит в `core:window:default`.

### Размер и положение

Их запоминает `tauri-plugin-window-state` — размер, координаты и развёрнутое состояние,
в файле рядом с данными приложения. Плагин **сохраняет всегда**: на каждое перемещение,
изменение размера и при закрытии окна. Восстанавливает — **только по просьбе**: он
подключён с `skip_initial_state`, и команду `plugin:window-state|restore_state` вызывает
`use-window.ts`, если включён переключатель «запоминать размер и положение».

Так у переключателя есть ровно один смысл — восстанавливать или нет, — и нет второго
хранилища, которое спорило бы с первым: геометрия больше не лежит в `localStorage`.
Запись, оставшаяся там от прежних сборок, отбрасывается при чтении настроек.

## Локальный интерфейс

```bash
pnpm --filter web build:desktop      # → apps/web/out/desktop
```

Скрипт — `apps/web/scripts/build-desktop.mjs`. Он ставит `MIXTURE_DESKTOP_BUILD=1`
(в `next.config.mjs` это включает `output: "export"`, `distDir: "out/desktop"` и
`trailingSlash: true`), запускает `next build` и обязательно возвращает дерево в исходное
состояние — и при успехе, и при ошибке, и по ^C. На время экспорта он:

| Что                          | Почему                                                                       |
| ---------------------------- | ----------------------------------------------------------------------------- |
| убирает `app/api`            | `/api/rpc` — это POST, `/api/cloud/stream` отвечает на `Range`; статической формы нет |
| убирает `app/manifest.ts`    | установленный `.exe` — не PWA                                                  |
| правит `dynamic` в `app/page.tsx` и `app/insert/[id]/page.tsx` | `force-dynamic` несовместим с экспортом  |
| правит `dynamicParams` в `app/insert/[id]/page.tsx` | в экспорте маршрут — это файл, спрашивать некого       |

Директивы сегмента маршрута Next разбирает из текста, а не вычисляет, поэтому флаг внутри
страницы их не переключит — правится сам литерал. Замена, которая ничего не нашла,
роняет сборку: переименованная директива обязана сломать сборку, а не тихо выпустить
бандл, чьи страницы всё ещё ждут сервер.

`/insert/<id>` в экспорте — это набор файлов: `generateStaticParams` перечисляет
встроенный каталог и сгенерированные пакеты вставок (ровно то, что `fetchLibrary()`
отдаёт без `DATABASE_URL`), а `dynamicParams = false` закрывает остальное. У вставки,
добавленной через библиотеку в базу, полноэкранной страницы внутри оболочки нет — в
списке и в превью она работает как любая другая.

Сам бандл берёт экспорт из `frontendDist` (`../../web/out/desktop`), а
`beforeBuildCommand` запускает экспорт сам, поэтому локально достаточно:

```powershell
pnpm --filter @mixture/desktop tauri build
```

## Какой api открывает приложение

Транспорт rpc берёт адрес из `DEFAULT_RPC_SETTINGS.baseUrl`
(`apps/web/lib/rpc/settings.ts`). Значение приходит из `NEXT_PUBLIC_MIXTURE_API_URL`,
который `next build` подставляет в код при экспорте; рабочий процесс релиза задаёт
`https://mixture-codeilluminators.vercel.app`. В веб-сборке переменной нет, значение
остаётся пустым и означает «тот же origin, что и у страницы» — как и раньше.

Пустое значение внутри оболочки означало бы `tauri://localhost`, где api нет вовсе,
поэтому в десктопной сборке к пустому origin ничего не откатывается: и очищенный, и
отклонённый пользовательский адрес возвращаются к тому, с которым собран бандл.

Указать другой стенд можно **без пересборки** — в разделе «настройки» → «rpc», поле
«базовый адрес»: `https://…` (или `http://localhost:…` для сервера на этой же машине).
Адрес хранится в `screenkit-rpc-v1`, проверяется `checkBaseUrl` (https или петля, без
`user:password`) и действует со следующего вызова.

### Кросс-доменный доступ к api

Страница открывается с `tauri://localhost` (в Windows — `http://tauri.localhost`), а api
живёт на другом origin, поэтому webview требует CORS: заголовки `x-grpc-web`,
`connect-protocol-version` и три заголовка с токенами делают предзапрос `OPTIONS`
обязательным.

Маршрут `/api/rpc` отвечает на него сам — `lib/rpc/cors.ts` держит список origin, которым
это разрешено:

- оба адреса оболочки (`tauri://localhost`, `http://tauri.localhost` и его https-форма) —
  всегда;
- origin из `NEXT_PUBLIC_SITE_URL`, если он задан;
- всё, что перечислено через запятую в `MIXTURE_RPC_ALLOWED_ORIGINS`.

Ответ повторяет запрошенный origin, а не `*`, и `Vary: Origin` не даёт кэшу отдать чужой
ответ. Звёздочка здесь недопустима намеренно: интерцептор `credentials` прикладывает к
каждому запросу токен редактирования и github-токен пользователя, так что origin в списке
— это origin, которому эти токены достанутся. Origin не из списка получает `403` без
единого заголовка `Access-Control-*`.

## Политика безопасности контента

`app.security.csp` в `tauri.conf.json` применяется к странице, которую Tauri отдаёт с
диска (в `tauri dev` страницу отдаёт Next, и туда CSP не подставляется).

| Директива                | Значение                                            | Почему                                                                     |
| ------------------------ | --------------------------------------------------- | -------------------------------------------------------------------------- |
| `default-src`            | `'self'`                                            | всё, что не перечислено ниже, — только из бандла                            |
| `script-src`             | `'self' 'unsafe-inline'`                            | код только свой; встроенный скрипт темы в `app/layout.tsx` Tauri подписывает хешем при сборке. `'unsafe-eval'` не нужен: в экспорте нет ни `eval(`, ни `new Function(` |
| `style-src`              | `'self' 'unsafe-inline'`                            | инлайновые стили компонентов                                                |
| `img-src` / `media-src`  | `'self' data: blob: asset: http://asset.localhost https: http:` | вставка-файл показывает картинку или видео по произвольному http(s)-адресу, локальные файлы приходят через asset-протокол |
| `frame-src`              | `'self' data: blob: https: http:`                   | вставка-сайт — это `<iframe>` на произвольный адрес                         |
| `connect-src`            | `'self' data: blob: ipc: http://ipc.localhost asset: http://asset.localhost https: http://localhost:* http://127.0.0.1:* http://[::1]:*` | rpc идёт на удалённый api, а адрес меняется в настройках без пересборки — поэтому не один origin, а `https:` и петля, ровно то, что пропускает `checkBaseUrl` |
| `object-src`             | `'none'`                                            | плагинов нет                                                                |
| `base-uri`, `form-action`| `'self'`                                            | подменить базовый адрес или отправить форму наружу нельзя                   |
| `frame-ancestors`        | `'none'`                                            | окно приложения никто не встраивает                                         |

## Права: отладка и релиз

Файлов в `src-tauri/capabilities/` два, и различаются они только тем, к какому источнику
относятся.

- `default.json` — **локальный**: блока `remote.urls` в нём нет, потому что интерфейс
  теперь лежит в бандле и открывается с `tauri://localhost`. Права те же, что и раньше,
  плюс поимённое управление окном (таблица в начале).
- `dev.json` — тот же список для `http://localhost:3000`, единственного адреса, который
  открывает `tauri dev` через `build.devUrl`.

Сборка, не назвавшая набор, включает **оба файла**; релизная называет: рабочий процесс
подставляет `app.security.capabilities: ["default"]` в накладке конфигурации, поэтому в
опубликованном приложении localhost прав окна не получает.

## Сборка на Windows

Нужны Node 22+, pnpm 10.34, Rust (stable, MSVC) и Microsoft Edge WebView2 (в Windows 11
он уже есть, в Windows 10 установщик подтянет его сам).

```powershell
pnpm install
$env:NEXT_PUBLIC_MIXTURE_API_URL = "https://mixture-codeilluminators.vercel.app"
pnpm --filter @mixture/desktop tauri build
```

Результат — `apps/desktop/src-tauri/target/release/bundle/nsis/*.exe` и `.../msi/*.msi`
(`bundle.targets` в `tauri.conf.json` — `["nsis", "msi"]`). Под конкретную архитектуру
есть готовые скрипты: `build:x64`, `build:arm64`, `build:x86` — каждый собирает NSIS и
MSI для своего триплета.

Разработка: `pnpm --filter web dev` в одном терминале и
`pnpm --filter @mixture/desktop tauri dev` в другом — отладочная сборка открывает
`build.devUrl`, то есть `http://localhost:3000`, и экспорт для неё не нужен. Корневой
`pnpm dev` (`turbo run dev`) поднимает обе задачи сразу; для одного только сайта
используйте `pnpm --filter web dev`.

Иконки в `src-tauri/icons` — временные, они рисуются скриптом без внешних зависимостей:

```bash
pnpm --filter @mixture/desktop icons
```

## Сборка в CI

Задач две, в двух разных рабочих процессах, и они не пересекаются:

| Задача              | Где                                                             | Когда                                      | Что делает                                                          |
| ------------------- | --------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| `check`             | [`desktop.yml`](../../.github/workflows/desktop.yml)              | pull request, задевающий `apps/desktop/**` | ubuntu: `cargo check --locked --all-targets` и `cargo test --lib`   |
| `windows <arch>`    | [`release.yml`](../../.github/workflows/release.yml)              | коммит в `master`, прошедший `ci`          | windows-latest: Tauri CLI собирает NSIS, MSI и переносимую сборку   |

Готовые файлы берутся из релиза, а не из артефактов прогона: каждый зелёный коммит в
`master` публикуется как GitHub Release — см. [`docs/release`](../release/README.md).
`desktop.yml` больше ничего не собирает, чтобы тег не запускал сборку оболочки дважды.

## Какой файл брать

| Файл                                    | Кому                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------ |
| `...-windows-x64-setup.exe`             | обычный случай: 64-разрядная Windows 10 или 11                           |
| `...-windows-x64-setup-offline.exe`     | та же машина, но без интернета: WebView2 внутри файла (+~130 МиБ)        |
| `...-windows-x64-setup.msi`             | развёртывание через GPO, Intune или SCCM                                  |
| `...-windows-x64-portable.zip` / `.7z`  | без установки: распаковать и запустить `mixture-screenkit.exe`            |
| `...-windows-arm64-*`                   | Windows 11 на ARM и Windows 10 на ARM; offline-варианта у ARM64 нет       |
| `...-windows-x86-*`                     | 32-разрядная Windows 10                                                   |

Правило простое: если не знаете разрядность — `x64-setup.exe`. На 64-разрядной системе
x86-сборка запустится через WoW64, но смысла в ней нет.

Переносимая сборка — это один `.exe` без установщика и без среды выполнения. Она
**не ставит WebView2**: на машине, где его нет, окно будет пустым. Тогда либо возьмите
установщик, либо поставьте
[Evergreen Bootstrapper](https://go.microsoft.com/fwlink/p/?LinkId=2124703) руками.

## Совместимость с Windows

Минимум — **Windows 10 версии 1803 (сборка 17134)** и Windows 11. Порог задаёт не
приложение, а Microsoft Edge WebView2: на более старых сборках Evergreen-среда выполнения
не устанавливается, а без неё окно нечем рисовать. Windows 7, 8 и 8.1 отпадают по той же
причине — поддержка WebView2 для них прекращена.

Архитектуры — x64, ARM64 и x86; собираются все три. Порог версии среды выполнения —
`minimumWebview2Version: "110.0.0.0"`, первая версия WebView2 без поддержки Windows
7/8/8.1 — рабочий процесс релиза дописывает только к обычному установщику. Если на машине
WebView2 старее порога, обычный установщик обновляет его через EdgeUpdate по сети и
прерывает установку, когда это не удалось. У offline-установщика порога нет: он для того
и существует, чтобы поставить вложенную среду выполнения там, где сети нет. Подробности —
[`docs/release`](../release/README.md).

Сборки **не подписаны**: при первом запуске Windows SmartScreen покажет «Windows защитила
ваш компьютер», открыть — «Подробнее» → «Выполнить в любом случае». Проверить файл можно
по `SHA256SUMS.txt` из релиза. Как включить подпись сертификатом — в
[`docs/release`](../release/README.md).

## Доступ к локальным файлам

Вкладка «облако» умеет показывать локальную папку так же, как репозиторий облака.
Контракт один на все среды — `LocalFsBridge` (`apps/web/lib/local/bridge.ts`), а
реализаций три: браузерная (File System Access API), десктопная (команды Tauri) и
мобильная. Выбор делает `localBridge()` (`apps/web/lib/local/index.ts`): внутри оболочки
— Tauri, иначе браузер. `@tauri-apps/api` подгружается лениво, поэтому обычная вкладка
браузера его не скачивает.

Что видит пользователь:

1. Экран разрешения (`components/screenkit/local/permission-screen.tsx`) объясняет, что
   будет прочитано: имена, типы и — при открытии файла — содержимое.
2. Кнопка «выбрать папку» открывает системный диалог Windows. Выбранная папка
   запоминается в `local-root.json` в каталоге данных приложения, поэтому после
   перезапуска спрашивать заново не нужно.
3. Сразу после выбора идёт обход папки: количество файлов и подпапок, объём, топ
   расширений. Больше 5000 записей — сводка помечается как усечённая.
4. Кнопка «забыть» удаляет запомненный путь; «сменить» открывает диалог снова.
5. Если папка исчезла (отключённый диск, переименование), команда `local_permission`
   отвечает `prompt`, и экран разрешения возвращается.

### Границы

Каждая команда получает путь относительно выданной папки, в posix-виде. Перед любым
обращением к диску путь нормализуется и проверяется (`apps/desktop/src-tauri/src/local.rs`):

- `..`, пустые сегменты и `.` разворачиваются; выход выше корня — ошибка;
- сегмент с `:` (буква диска, NTFS-поток) или управляющим символом отклоняется;
- существующий путь канонизируется, и результат обязан начинаться с канонического корня
  — симлинк, ведущий наружу, отклоняется, а не разыменовывается;
- для ещё не существующего файла проверяется ближайший существующий родитель, поэтому
  запись через подменённую папку тоже не пройдёт;
- удалить саму выданную папку нельзя.

Наружу, в веб-вью, абсолютные пути не уходят — кроме одного случая: `local_stream_url`
возвращает абсолютный путь, который бридж тут же передаёт в `convertFileSrc`, чтобы
`<img>` и `<video>` читали файл через asset-протокол без копирования в память. Выданная
папка добавляется в область asset-протокола в рантайме (в `tauri.conf.json` она пустая:
на момент сборки папка ещё не известна).

Права окна перечислены в `src-tauri/capabilities/`: ядро, управление окном (таблица
выше), `shell:allow-open`, `dialog:allow-open` и файловая система в каталоге данных
приложения. Подробности — в разделе «Права: отладка и релиз».

| `local_remove`       | `path`               | —                                            |

## Оболочка окна: панель, настройки, экран без сети

Три части десктопной оболочки живут на стороне сайта, а не в Rust: верхняя панель вместо
системного заголовка, карточка настроек окна и полноэкранный экран «нет сети». Все они
проверяют рантайм через `isTauriRuntime()` (`apps/web/lib/local/bridge.ts`) и вне Tauri
не рисуют ничего, поэтому веб-сборка остаётся прежней. `@tauri-apps/api/window`
импортируется лениво — внутри эффектов и обработчиков, — так что в браузере этот модуль
не загружается.

| Что                | Где                                                     |
| ------------------ | ------------------------------------------------------- |
| панель             | `apps/web/components/screenkit/desktop/titlebar.tsx`     |
| кнопки окна        | `apps/web/components/screenkit/desktop/window-controls.tsx` |
| работа с окном     | `apps/web/components/screenkit/desktop/use-window.ts`    |
| настройки          | `apps/web/components/screenkit/desktop/desktop-settings.ts` |
| карточка настроек  | `apps/web/components/screenkit/settings/desktop-settings.tsx` |
| экран без сети     | `apps/web/components/screenkit/offline-screen.tsx`        |
| состояние сети     | `apps/web/lib/net/online.ts`                              |
| строки             | `apps/web/lib/screenkit/i18n/desktop.ts`                  |

### Верхняя панель

Полоса высотой 40 пикселей (32 в компактном режиме) с названием приложения, текущим
разделом, необязательными часами и тремя кнопками окна: свернуть,
развернуть/восстановить, закрыть. Кнопки — обычные `<button>` с `aria-label` из словаря
и видимым фокусом: у окна без рамки нет системных кнопок, на которые можно опереться.
Закрытие подсвечивается цветом `--danger`.

Сама полоса и её пассивные дети помечены `data-tauri-drag-region`, поэтому окно тянется
за любое место панели, кроме кнопок. Двойной щелчок по региону разворачивает и
восстанавливает окно; обработчик сначала сверяет состояние окна с тем, каким оно было в
момент нажатия, — если оболочка Tauri уже переключила его сама, второе переключение не
отменяет первое.

Панель — обычный флекс-элемент над строкой «рельса + контент» в `app-shell.tsx`, а не
плавающий слой: строка ниже растягивается по `flex-1` и сама вычитает высоту панели, без
отступов и смещений. Высота дополнительно публикуется в `--sk-titlebar-h` на `<html>` —
её читает экран «нет сети», чтобы не закрывать кнопки окна. В `globals.css` переменная
равна `0px`, и на вебе перекрывать её нечем.

### Настройки

Карточка «десктоп» в разделе «оформление», после карточки плеера. В браузере она
показывает одну строку о том, что настройки живут в десктопном приложении, — вместо
переключателей, которым нечем управлять.

| Группа          | Настройка                            | По умолчанию |
| --------------- | ------------------------------------ | ------------ |
| окно            | поверх всех окон                     | выключено    |
| окно            | открывать развёрнутым                | выключено    |
| окно            | запоминать размер и положение        | включено     |
| окно            | минимальный размер                   | 720 × 560    |
| верхняя панель  | показывать панель                    | включено     |
| верхняя панель  | компактная высота                    | выключено    |
| верхняя панель  | сторона кнопок                       | справа       |
| верхняя панель  | часы                                 | выключено    |
| верхняя панель  | название раздела                     | включено     |
| верхняя панель  | акцентная линия                      | выключено    |

Всё это хранится в `localStorage` под ключом `screenkit-desktop-v1` и читается через
`normalizeDesktopSettings`: испорченное поле откатывается к значению по умолчанию
поодиночке, а неправдоподобная геометрия (окно меньше 320 пикселей по стороне или
координата за пределами любого монитора) отбрасывается целиком, чтобы окно не открылось
там, где до него не дотянуться.

«Поверх всех окон» применяется через `setAlwaysOnTop` при изменении и при запуске.
Размер и положение сохраняются по событиям `onResized`/`onMoved` с задержкой 400 мс и
восстанавливаются на старте через `setSize`/`setPosition` в логических пикселях.
Развёрнутое окно не запоминается: его прямоугольник — это монитор, и восстановить такое
окно как обычное значит открыть неразвёрнутое окно во весь экран.

### Экран без сети

`apps/web/lib/net/online.ts` держит состояние связи: `navigator.onLine` плюс события
`online`/`offline`, плюс проба доступности — `HEAD` на `/manifest.webmanifest` того же
origin, что и rpc-маршрут, с таймаутом 5 секунд. Проба идёт при старте, при событии
`online`, каждые 20 секунд, пока связи нет, и по кнопке «повторить». В Tauri она
повторяется ещё и каждые 60 секунд при живой связи: десктоп зависит от удалённого api,
и мёртвый сервер для него неотличим от обрыва.

Отсюда два вердикта, и разница между ними намеренная: в браузере оверлей реагирует
только на `navigator.onLine`, а недоступный сервер сам по себе офлайном не считается —
вкладка загружена и работает на встроенной библиотеке. В десктопной оболочке
недоступный сервер — это офлайн. Успешная проба важнее устаревшего `navigator.onLine`,
обратное неверно: обрыв связи сбрасывает результат последней пробы.

Оверлей закрывает всё ниже панели окна, показывает причину, кнопку «повторить» и
«продолжить без сети». Второй вариант убирает экран до конца сессии — встроенные вставки
и локальные файлы работают и без сети. Когда проба проходит, экран исчезает сам и
появляется тост «соединение восстановлено». Язык берётся из `screenkit-locale`, по
умолчанию русский; до монтирования компонент не рисует ничего, поэтому гидратация не
расходится.

## Чего здесь нет

Автообновления, подписи кода, сборок для macOS и Linux и отдельного десктопного
интерфейса: интерфейс — то же веб-приложение, только распакованное в бандл. Полноэкранной
страницы у вставки, добавленной через библиотеку в базу, внутри оболочки тоже нет: в
экспорте маршрут — это файл, а такой вставки на момент сборки не существовало.

Сеть нужна только прикладным операциям. Само окно открывается без неё: библиотека,
превью, подсказки и локальные файлы работают на том, что лежит в бандле. С сетью
добавляются облако, changelog и вставки из базы — их отдаёт api, к которому оболочка
ходит кросс-доменно (см. «Кросс-доменный доступ к api»).
